## Core change: semantic visibility

**Natural language is defined over ALL VISIBLE COMPONENTS. Eligibility may
reject a sample; it may never silently change its answer.**

v0.1 asked the relation engine, which answers over an *eligibility-filtered*
subset, then rendered the answer in language that reads as being over *all
visible* components. Whenever the true global extreme was excluded by
border/tiny/merge quality logic, the emitted instruction was false. A Task 5
audit measured **7,086 of 32,284 records (21.9%)** affected.

v0.1.1 inverts the order:

1. compute the **semantic** answer over every visible component;
2. check whether that exact component is admissible (eligibility + frozen margin);
3. admissible -> keep the query;
4. otherwise -> **discard it**. The runner-up is never substituted.

| Question | Resolved over | Kept only if |
|---|---|---|
| `largest` / `smallest` | global argmax / argmin of `area_px` over all visible components | that component is eligible **and** `larger/smaller >= 1.10` |
| `<ref>_to_nearest` | boundary distance to all other visible components | the true nearest is nearest-eligible **and** passes the frozen margin |
| `<ref>_to_<direction>` | frozen direction predicate over all visible components | exactly one candidate |
| `<ref>_to_<dir>_to_nearest` | nearest within the **full** direction-valid set | that exact nearest is nearest-eligible **and** passes the margin |

One shared implementation enforces this for the generator, the target
recomputation and the validator: `spatial_reasoning/semantic_policy.py`.

## Independent acceptance oracle

A shared implementation proves *consistency*, not *truth*: if it is wrong, it is
wrong twice and the audit still says PASS. Task 5C therefore adds a second,
deliberately independent implementation used only for auditing —
`spatial_reasoning/semantic_oracle.py`.

The oracle **never imports or calls** `semantic_policy`. It re-derives
`largest` / `smallest` / `nearest` / `direction` / `direction->nearest` from raw
component geometry, the frozen config, the frozen direction predicate and its own
recomputation of the quality flags. Every one of the 25,229 records is then
resolved twice and compared field by field. See
`docs/build_spatial_reason_v0.1.1_quality_audit.md` for the result.

## ID-free natural-language reasoning

`reasoning_zh` / `reasoning_en` contain **zero** internal component ids. The
structured `reasoning_steps` keep numeric ids for machine verification; the prose
explains the operation in role terms instead.

v0.1 (leaked ids):

```
reasoning_zh : 最左侧的建筑区域是 component 2。
```

v0.1.1 (role-based, ID-free):

```
reasoning_zh : 首先确定图像中最左侧的建筑区域，将其作为参考区域。
reasoning_en : First identify the leftmost building region as the reference region.
```

Level-3 example:

```
reasoning_zh : 首先确定图像中面积最大的建筑区域，将其作为参考区域。随后筛选位于参考区域右侧的建筑区域。最后比较这些候选区域与参考区域的边界距离，选择距离最近的区域作为目标。
reasoning_en : First identify the largest building region as the reference region. Then identify the building regions on the right side of the reference region. Finally compare their boundary distances to the reference region and select the nearest one as the target.
```

**Why this matters:** the input image displays no component ids. Prose that
references them teaches a model to emit identifiers it cannot ground, which is an
annotation artifact rather than spatial reasoning.

## Explicit `template_id`

Every sample now records `template_id` (e.g. `l3.chain.a`). It is deterministic,
the **same id** applies to the zh/en pair, and the validator independently
re-verifies that the rendered zh/en text matches the recorded id. Previously only
`template_version` was stored, so language diversity could not be audited without
reverse-engineering the text.

---

## Distractor policy

`distractor_component_ids` now excludes **both** the target and **every explicit
reference**. A reference is reasoning context, not a wrong answer. In v0.1 the
reference appeared in distractors for 12,918 records (40.0%).

Internal candidate sets used for reasoning are separate and may retain members
that the direction/nearest logic needs.

---

## Level-2 statistics

Type A = `level == 2` **and** `*_to_nearest`.
Type B = `level == 2` **and** one-hop `reference -> direction`.

Generation raises an assertion, and the audit fails, if:

```
level2.reference_to_nearest + level2.reference_to_direction != by_level["2"]
```

v0.1's counter omitted the `level == 2` guard, so `endswith("_to_nearest")` also
matched every Level-3 type and reported 8,700 instead of the true 4,707.

## Frozen rules (unchanged)

- Predicate convention `relation(subject, object)` = subject satisfies the
  relation w.r.t. the object (ADR-006).
- `ratio_margin = 1.10`; direction preset `medium` (`alpha = 1.2`, `tau = 0.04`);
  presets monotonic (ADR-008).
- `nearest`: anchor non-border **and** target non-border (ADR-007).
- Ambiguity -> **discard**, never tie-break (ADR-004).
- Scope: tile-relative spatial reasoning.

## Sample counts

See `statistics.json` for the authoritative values. No count target was imposed;
the corrected generator and the existing quota logic determined the total. Because
semantic filtering removes samples whose answer the eligibility rules would have
changed, v0.1.1 is **smaller** than v0.1 — that is the intended trade
(correctness over volume).

Level-3 is still split into **trivial** and **nontrivial**:

- **nontrivial** — more than one admissible candidate after the direction filter,
  so a real distance comparison is required;
- **trivial** — exactly one admissible candidate; the filter alone determines the
  answer.

The primary multi-hop metric should use the **nontrivial** subset; trivial
samples are reported separately and are **not** deleted.

## What this dataset can evaluate

- Direct spatial grounding (`leftmost` / `rightmost` / `topmost` / `bottommost` /
  `largest` / `smallest`)
- Reference-based reasoning (`reference -> nearest`, `reference -> direction`)
- Multi-hop geometric reasoning (`reference -> direction -> nearest`)
- Target segmentation

## What it must NOT be claimed to provide

- Physical-building instance ground truth (components are connected components).
- Building functional semantics (no use/type annotation exists).
- General world reasoning (all queries are geometric and tile-relative).
- Façade / indoor structure understanding.

## Known limitations

1. **Source annotation is connected components**, not verified physical
   buildings. Mutually touching buildings were merged before this dataset existed.
2. **Border-truncated components are excluded** from `largest` / `smallest` /
   `nearest`. Since the semantic answer must itself be eligible, images whose
   largest/smallest building touches the tile edge simply produce **no** query for
   that type. This reduces coverage but never produces a false instruction.
3. **No building-function semantics** in the source data.
4. **No overlap / containment relations** — components are disjoint by
   construction.
5. **Language is template-generated**, so wording diversity is bounded by the
   template families. `template_id` is now recorded to make this auditable.
6. **Scene-level split leakage is `unverified`** — the derived dataset carries no
   scene/geographic grouping metadata, and val was a random 20% subset of the
   original train pool. Exact image duplication is ruled out (0 byte-identical
   cross-split images); geographic adjacency is not.
7. **Tile-edge truncation is a cropping artifact**, not a property of buildings.
   v0.1.1 therefore filters such samples out instead of naming the eligibility in
   the instruction (see ADR-010, rejected alternative).
8. **Scene/viewpoint wording.** All queries are defined within a single 512×512
   tile; "leftmost" means leftmost *in this tile*.
